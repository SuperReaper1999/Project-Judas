## 2. Paired stick input without axis-deadzone distortion

Claude needs the two physical stick axes together, before the engine's individual
axis deadzones/scales destroy their direction. A suggested raw API is:

    input.stick('right')  // {x, y}; also support 'left'

Choose names consistent with current JudasJS. Provide the following contract:

- Return a copied pair of normalized device-axis values, each in [-1, 1], before
  engine deadzone, sensitivity, smoothing or response-curve processing. Raw here
  means before Judas's processing, not bypassing controller firmware/OS behaviour.
- Read both axes from the same selected controller. Reuse existing normalization,
  device assignment and sign conventions; document them. Do not reconstruct raw
  values from already processed logical axes. Do not clamp raw diagonals to a unit
  circle: raw components and a processed movement vector are different products.
- Keep current button, trigger, keyboard/mouse, scalar-axis and controller mappings
  compatible. Do not silently change every existing binding's deadzone behaviour.
- Follow normal gameplay input focus/capture rules. No controller returns a defined
  neutral result. Disconnect, controller reassignment, focus loss and session
  changes must not fabricate a flick or leave stale movement pending.

Add a paired-stick/vector binding with an explicit optional circular deadzone in
the normal input map. It must load/save through the existing supported legacy and
M67 named-authoring paths, with the normal validation and existing input inspector
where applicable. Preserve old bindings and defaults. No new input-map language
or replacement editor.

Define the radial response instead of merely calling two independent axis
processors. A suitable default for the NEW circular mode is:

    v = raw paired vector; m = length(v); inner deadzone d satisfies 0 <= d < 1
    if m <= d: output = (0, 0)
    otherwise: output = (v / m) * min(1, (m - d) / (1 - d))

This preserves direction outside the deadzone and rescales usable travel. Reuse
an equivalent existing radial processor if present. Reject invalid/non-finite
configuration, apply processing once, and keep raw reads unaffected. Document how
paired bindings interact with supported inversion/scaling. Game scripts must be
able to read BOTH the raw pair and the mapped circular-deadzone result.

### Fast flicks and frame/fixed-step delivery

Claude would also use a render-frame reading and movement since the last frame.
Provide the latest frame sample and clearly defined frame delta through the
normal input service; readings must not update only when physics steps.

However, neutral -> diagonal -> neutral can finish between fixed steps, and its
net delta is zero. Endpoints plus delta alone do not preserve that movement.

Retain a small bounded history of the paired observations delivered by the
existing backend event/input pump, reusing an existing event history if suitable.
Expose it through a minimal supported API so game JS can process ordered movement
samples even when no fixed step happened between them. Include monotonically
ordered sample IDs and usable timing information; document timing/units and
reset behaviour. Repeated readers must not steal samples from another script.
A cursor/sequence-based snapshot API is sufficient; no new input framework.

Specify capacity and detectable overflow/reset behaviour. Do not silently present
a truncated movement as complete. Ensure the game can recognize new observations
once across zero, one or multiple fixed steps and avoid a burst of stale actions
after pause, focus loss or scene change. Keep authoritative gameplay on its normal
fixed-step boundary; do not move physics into a render callback to catch flicks.

Do not claim to recover movement the device/backend never delivered. A bounded
input sample history is in scope; recording/replaying worlds, custom HID drivers,
background polling threads, rollback networking and a general replay system are not.

## 3. Batched queries: one JS-to-native call, existing collision mathematics

Required: a synchronous nearest-hit ray batch, with up to 256 entries per call.
Claude's suggested shape is:

    physics.raycastMany(rays, filter)
    // rays: [{origin, direction, maximum}, ...]
    // results: one corresponding hit/miss per input, in the same order

Use the current scalar API's names, coordinate conventions and result fields.
Use null for misses only if that matches the existing scalar convention; otherwise
retain its normal miss representation. Document the actual shipped signature.

- Cross the JS/native bridge ONCE for an accepted batch, validate/prepare the common
  filter once, then iterate the existing query service natively. A JS map that calls
  physics.raycast 100 times does not solve this request.
- Reuse normal broadphase/narrowphase, nearest-hit selection and filtering. Preserve
  layers/masks, tags, sensors, exclusions, generation-safe handles and existing
  disabled/destroyed-object rules. Do not introduce alternate collision geometry.
- Maintain input order, including misses and repeated queries. Empty input returns
  an empty result. Do not sort, truncate, or silently split an oversized call.
- Validate the whole bounded request before executing queries. Reject malformed
  entries or >256 queries with useful indexed diagnostics and no partial result.
  Preserve scalar rules for finite values, directions, distance and overlaps.
- Execute against the same authoritative world and legal query phase as scalar
  calls. Do not advance simulation or deliver script callbacks halfway through a
  batch. No copied world, worker query scheduler, asynchronous result handles or
  alternative snapshot engine is needed for this synchronous operation.
- Results follow existing snapshot/lifetime semantics and use safe entity handles,
  not pointers into temporary storage. Preserve arbitrary orientations and the
  existing large-coordinate representation; no world-up or legacy-player shortcut.

Add sphereCastMany and capsuleCastMany as well IF they are thin bounded wrappers
around existing scalar query/marshalling paths. That is Claude's requested cheap
extension, not permission to invent new shape algorithms or a generic query DSL.
If either requires substantial new machinery, ship the required ray batch and
state the specific deferred extension/reason. Do not add box/overlap/all-hit batch
families merely for symmetry.

The goal is approximately 100 ledge-scan rays per step without 100 bridge calls,
not fewer real geometric queries. Do not promise an arbitrary speedup or claim
this automatically makes a 200-query game affordable on every machine.
