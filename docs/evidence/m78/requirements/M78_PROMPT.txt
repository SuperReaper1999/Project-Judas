## 5. Per-capability investigation procedure

For each register row, do the following in proportion to risk:

1. State a falsifiable expected behaviour, supported inputs/limits and its source
   reference. Identify any later approved change. Keep human acceptance separate.
2. Trace the real public/editor/native entry through state ownership and update
   ordering to the effect. Record relevant paths/symbols at the frozen commit.
   Identify who writes state, applies forces, resolves resources and publishes it.
3. Inspect the current test and fixture. Explain what would make it fail if the
   feature were missing, disconnected or wrong. Reused expected-value code,
   mere getters, mocked mechanisms and fixtures that directly set the claimed
   outcome are not independent proof of that outcome.
4. Execute an ordinary successful case and a meaningful adversarial/negative case
   for the mechanism. Use existing public paths for delivered user-facing claims.
   Where safe, vary identity, pose/orientation, proportions, topology, counts or
   lifecycle within the supported range to expose demo-specific assumptions.
5. Declare comparison criteria before judging new results. Use independent analytic
   references, paired on/off controls, equivalent transforms or differential
   observations where appropriate. Distinguish a numerical tolerance, source-data
   approximation, subjective quality goal and observed performance sample.
6. Capture command, exact input/binary identity, environment, assertions, exit code,
   logs and output measurements. A screenshot or a completed process alone does
   not establish physics, saving, timing or human usability.
7. Classify the result and remaining coverage. Reduce failures to small repros
   without changing the failure condition. Validate that the observer itself is
   sane. Preserve failed receipts, timeouts, skips and environmental blockers.

Inspection for suspicious mechanisms must be specific: scene/entity/bone names
choosing engine behaviour; decorative motion substituted for claimed physics;
state/velocity resets; missing reactions or duplicate authority; hidden clamps,
repairs or thresholds; divergent editor/runtime paths; stale identities; unbounded
scans; assert-disabled tests; cached success from old binaries; and ignored faults.

These patterns are investigation leads, not automatic guilty verdicts. An explicit
teleport API, torque cap, bounded approximation, game-script policy, numerical
stabilization or external work from a kinematic actuator can be legitimate.
Explain whether it matches the stated contract and whether energy/momentum/work
is accounted for. Do not flag every number or authored policy as a cheat.

Use negative controls without polluting production. Prefer public effort/feature
off, denied permission, malformed input or missing-resource cases. Any deliberate
mutation belongs only to a separate audit copy, and is not an engine fix or a
claim that the unmodified engine exhibited the injected fault.

## 9. Capability register and findings format

Maintain one compact authoritative machine-readable register with a human-readable
summary, not three divergent hand-maintained inventories. Stable feature IDs should
link the requirement crosswalk, test cases, findings and human checklist.

Each feature record should include:
- Feature/subsystem and lifecycle/combination being claimed.
- Contract source, exact supported envelope/units, historical supersession and any
  unresolved requirement-versus-documentation discrepancy.
- Actual ownership/entry points and source paths/symbols at the frozen commit.
- Linked tests, independent oracle/negative control and declared tolerances.
- Execution status per platform, input/binary identities, commands and receipts.
- Observed values/errors and scope of evidence, not merely PASS.
- Known limitations, untested combinations and human/hardware acceptance separately.
- Findings/repro IDs, severity and proposed correction boundary, without fixes.

Keep at least these dimensions independent:
  Implementation: present / partial / absent / intentionally unsupported / unknown.
  Behavioural evidence: verified-within-envelope / partially verified / failed /
                        blocked / not-executed / not-applicable.
  Acceptance: operator accepted / human review pending / hardware pending,
              each with its own scope, date and checkpoint when available.

A source-only inspection is not an execution pass. A failed required behaviour
cannot be relabelled untested. An intentionally absent feature is not a bug unless
it was promised. Marking one sampled case verified does not erase uncovered inputs.

For every finding provide the claim, expected versus actual result, smallest
reproduction, affected entry points and versions, determinism/frequency, platform,
raw evidence, impact/severity, known/new status, confidence and unresolved cause.
Distinguish engine, game-content, harness, documentation and environment defects.
Suggested fix boundaries are welcome; implementation is not authorized.

Coverage reporting must expose denominators: inventoried current features, traced,
executed on each platform, passed/partial/failed/blocked/unexecuted, and operator-only
checks. Do not weight trivial getters into a flattering global pass percentage or
call every subsystem verified because one aggregate test executable exited zero.
