## 2. One import service, normal assets, mature parsers

Provide one shared import/cook service used by editor and CLI. Required front ends:
- FBX, including the original character, animation-only files and static models.
- glTF 2.0 / GLB, including external buffers/images as well as embedded data.
- Existing OBJ/MTL ingestion and collision-source workflows must remain usable.

Use pinned ufbx for FBX unless a demonstrated incompatibility justifies another
mature permissively licensed parser. Reuse the existing cgltf path for glTF and
existing OBJ support; do not replace working front ends gratuitously. Pin exact
versions/commits and hashes, retain licenses/provenance, and use matching dependency
source/header versions. Primary references are listed in M66_SOURCE_NOTES.md.

Do not write an FBX parser. Use the library's transform/animation evaluation rather
than hand-decoding raw FBX Euler curves and pivots. Parser support alone does not
mean Judas supports every deformation or material the file can describe.

Pipeline:
source files + import settings + resolved dependencies
  -> validated normalized model/rig/clip/material data
  -> ordinary versioned runtime assets and stable subasset references
  -> existing ResourceManager / RuntimeWorld / Renderer.

Choose the smallest coherent extension of current asset formats; a normalized
GLB-based representation or an appropriate cooked asset can work. Do not create a
second AssetDatabase or animation runtime. Runtime assets contain no parser-owned
pointers. Raw source files stay intact, and generated data records its provenance.
Validate counts, indices, finite transforms/weights and recursion/allocation bounds.
Malformed assets must fail usefully, not crash or allocate without bounds. External
file access follows explicitly approved import roots/remaps, not arbitrary paths
embedded in a downloaded model.

The supported user workflow must not depend on Blender, Python conversion scripts,
an Autodesk installation, a cloud service or an import-time network download.
DCC tools may create independent test fixtures/reference measurements, not secretly
perform a required production conversion. Existing format users keep working.

## 3. Transform and unit correctness

Normalize source coordinates once, consistently across geometry, hierarchy,
animations, skin bindings, collision sources and attachment targets.

- Read FBX axis/unit metadata. Provide visible deterministic overrides when metadata
  is absent/wrong. For formats without reliable unit metadata, show the assumption;
  do not guess from a filename or secretly rescale everything to human height.
- Preserve hierarchy, authored pivots and static mesh instances. Evaluate geometry
  transforms, pre/post rotations and inheritance correctly with the parser.
- Handle source centimetres/metres, rotated roots, mirrored static parts and baked
  nonuniform object scale. Correct normals, winding and tangent handedness together.
- Source normalization may produce unit-scale runtime physics assets; this does NOT
  authorize arbitrary dynamic nonuniform collider scaling in Judas.
- Apply the actual source-format skin semantics. Do not double-apply a skinned mesh
  node transform or collapse mesh-specific bind matrices into one skeleton-wide guess.
  Bind data, rest/default pose and the first animation frame are not interchangeable.
- Never project a required affine/sheared transform into an inaccurate TRS silently.
  Use a correct evaluated/baked representation where supported; identify unsupported
  deformations explicitly instead of reporting a successful but distorted import.

Preview dimensions, axes and a metre reference. Import-space up/forward conventions
are content conversion rules, not global gravity. Rotating the imported character
in a radial/oblique scene must not introduce a world-Y simulation assumption.

## 4. Multi-part models and practical skeleton capacity

Remove the one-mesh-node/48-joint bottleneck through the runtime path, not just parsing.

Required behavior:
- A character retains multiple skinned mesh nodes/primitives and material slots,
  including body, clothing and accessories. No compulsory mesh join or bone amputation.
- Several meshes can share a resolved skeleton while retaining their own skin-joint
  remaps and inverse-bind data. Static attachments can coexist with skinned parts.
- A source containing separate armatures must preserve that distinction. Import
  selection or hierarchy instantiation must not silently render only its first rig.
- Shared geometry/skeleton/clips remain immutable. Separate character instances own
  independent playback, final poses, part visibility and material overrides.
- Preserve nondeforming parents/helper nodes needed for animation, sockets, IK or
  hierarchy evaluation. Do not strip nodes merely because their direct skin weight is zero.

Use size-aware bounded storage and hardware-appropriate palette delivery. Preserve
skeleton identity independently of per-draw palette limits; batching/palette remaps
are allowed without deleting meaningful source joints or changing the asset's pose.
Do not replace 48 with another unexplained magic number throughout the code.

Minimum capacity proof: the original full rig, plus a generated 256-skin-joint
fixture whose high-index joints actually influence animated vertices. This is a
verification floor, not a requirement to allocate 256 matrices for every tiny model.
Support at least eight meaningful influences per vertex in a dedicated fixture.
Above supported bounds, reject clearly or offer an explicitly selected lossy profile
with a quantified reduction report; never silently truncate weights or joints.
Do not fold fingers into hands to pass the main character test.

Audit downstream fixed-size assumptions in pose composition, draw palettes,
shadows, bounds, editor pickers, sockets, IK, ragdoll mappings and saved state.
The full original character must render through main and secondary cameras and
shadows, not only a private import preview. Keep the existing graphics baseline;
no new rendering backend or high-end-GPU requirement.

## 5. Animation import and same-rig clip assembly

Import named takes/clips, including translation, quaternion rotation and scale.
Use correct source evaluation or bounded-error baking, and report sample/reduction
settings. Preserve discontinuities where the source requires them. Handle glTF
STEP/LINEAR/CUBICSPLINE correctly rather than silently treating all keys as linear.

Provide an editor/CLI workflow to:
- Add animation-only files to an imported compatible skeleton.
- Select takes, name/trim clips, set loop metadata and preview sampling.
- Assemble the original Push/Cruise/Walking files without manual NLA/export work.
- Reimport one motion file without rebuilding unrelated geometry/materials.

Match rigs using verified hierarchy/bind information and an explicit mapping when
needed. Do not assume source node indices match between files; short bone names
need not be unique. A compatible rig exported with reordered nodes should still work.
Ambiguous names, missing animated joints or incompatible rest geometry must identify
the conflict and allow correction, not bind to the first similarly named node.

Same-rig mapping and basis/unit conversion are required. Cross-species/proportion-
changing retargeting is not. Do not label a permissive name match as retargeting.

Clips remain ordinary pose producers in the M47 pipeline. Existing crossfades,
masks, additives and external producers must work with imported multi-part characters.

## 6. Root motion: usable data, not an automatic gameplay controller

Provide explicit per-clip policies:
- Preserve source motion.
- Bake in place using selected root-motion components.
- Extract selected motion into a separate time-addressable track while retaining
  the complementary pose.

The author chooses the motion node and model-space axes/components. A sensible
preview/default is fine; hardcoded Mixamo/Hips, Walk or Skate rules are not.
Removing planar travel must not accidentally remove crouch, pelvis bob, turning or
vertical jump motion that the author chose to preserve.

Define the decomposition and spaces. For extraction, applying the extracted motion
back to the complementary pose must reconstruct the source motion within declared
bake error. Preserve the initial offset convention. Correct interval sampling must
handle seeking, negative playback where supported and loop crossings without a
backward teleport or double-applied displacement.

Expose the extracted track through a small documented generic animation query so
ordinary JS can consume it; metadata hidden inside a cook file is insufficient.
A clip/time-interval query is acceptable without inventing a blended locomotion
framework. Report exactly what live-mixer sampling is and is not supported.

Animation must not directly move CharacterMotor, rigid bodies or the entity root.
Demonstrate a script optionally using sampled motion as motor intent, with a wall
proving collisions still win. In-place gameplay stays the default for existing
projects. Do not change Skate movement/trick rules merely to show root motion.

## 7. Materials, textures and model hierarchy

Retain M57's actual material semantics instead of importing geometry with arbitrary
default materials. Preserve stable primitive/part slots and supported base colour,
normal, metallic/roughness, emission, opacity/cutout and double-sided settings.

FBX material conversion must state its approximations. Unsupported shader graphs
must not be advertised as faithfully reproduced. Preserve source metadata and
provide an actionable warning/default for unsupported appearance features.

Resolve embedded and external image dependencies through the import service.
Handle source-relative paths, configured search locations, Windows path separators
and Unicode names on Linux. Ambiguous texture matches require an explicit choice;
no random first-match search across the user's disk. Copy approved dependencies
into project-owned storage and retain their dependency identities.

Keep colour textures and data maps in their correct existing colour-space paths.
Reuse pinned MikkTSpace when tangents need generation, with the selected normal-map
UVs, seams and reflections handled coherently. Support the ordinary UV0/UV1 texture
selections in focused fixtures; unsupported additional channels must be diagnosed,
not all silently mapped to UV0. Preserve supported sampler/UV-transform settings.

Imported defaults, project material remaps and per-instance overrides are distinct.
Reimporting a model must not overwrite a developer's separate material asset or
reset an instance override. Identical dependencies can share resources without
accidentally coupling independently editable material instances.

## 8. Identity, dependencies and transactional reimport

This is a deliverable, not optional cleanup after first import.

Persist an import recipe containing source identities, conversion settings,
parser/cooker revision, dependencies, stable generated subasset IDs, selections,
clip mappings and any explicit lossy/repair options. Use Judas's existing asset
identity/fingerprint infrastructure, not a competing registry.

Required guarantees:
- Unchanged input bytes/settings/dependencies under the same toolchain produce
  stable outputs and IDs. No timestamps, machine paths or process pointers in hashes.
- Changing a source mesh, external texture, motion file or setting invalidates its
  actual dependent products. Do not recompute everything on every frame or launch.
- Unaffected meshes, materials, clips and authored references keep their identities
  when source ordering changes. Maintain provenance/mapping; raw array indices and
  short names alone are not durable IDs.
- Renames/deletions with ambiguous correspondence are surfaced for remapping.
  Never retarget an old socket/IK/ragdoll reference to an unrelated replacement node.
- Cancellation, parse failure or crash before publication leaves the last accepted
  generation intact. Publish a coherent generation only after all required outputs
  and dependencies validate. Do not expose half of a new rig with half of an old skin.
- Keep last-good content available for inspection after failure, visibly marked
  stale. Do not silently export stale content against changed source/settings.
- Distinguish generated products from author-owned edits. Garbage collection may
  remove obsolete owned products only when references and author edits are safe.

Parsing/cooking/hashing run through existing background jobs with bounded work,
progress, cancellation and explicit main-thread/GPU publication. Use M65's corrected
bookkeeping; do not instantiate VMs to inspect assets or repeatedly scan all world
entities to rebind an unchanged model.

Live replacement during Play is not required: staging reimport until Stop/restart
is acceptable if explicit. Never mutate shared live rig buffers underneath physics,
sockets or Renderer. Source changes affect saved-world compatibility through the
existing policy; M66 must not silently reinterpret an old save against a new rig.

## 10. Environment content and collision-cooking diagnostics

Visual geometry and collision geometry remain separate. A renderable artist mesh
may be unsuitable as a collision surface without being an invalid visual model.
Do not block its visual import merely because an optional collision cook fails.

Integrate import selections with M64's existing cooker:
- Choose explicit source nodes/primitives or a separate physical-source file.
- Preserve source-to-cooked transforms, including import unit/pivot conversions.
- Offer existing static mesh, convex hull and selected-part compound/proxy choices
  through one ordinary workflow; show the resulting collision overlay.
- A hull that fills a quarter-pipe's playable concavity is NOT a successful matching
  ramp collider. Convex approximation is an explicit user choice with visible cost.

For bad winding, degenerates, T-junctions, nonmanifold edges and other checks the
cooker performs, report source file/node/mesh and original face/edge/vertex identifiers
where recoverable, coordinates/bounds and a selectable preview location. Carry
triangulation provenance so a cooked triangle index can be traced back to its source.
Do not fabricate text line numbers for a binary source.

Provide small explicit safe cleanup operations where justified: triangulation,
removing true degenerates, bounded duplicate-position welding for collision-only
geometry and orienting consistently orientable connected patches. Preserve render
UV/normal seams. Exact/locally validated T-junction splitting is acceptable if
implemented robustly; broad destructive repair is not a requirement.

Every geometry-changing repair operates on derived content, records its settings
and counts, and reruns validation. Never silently fill holes, merge unrelated
surfaces or relax seam/topology checks until the file passes.

Revisit the original artist half-pipe. If its nonmanifold/overlapping structure
cannot be safely repaired, point to the actual offending locations and provide a
practical separate-source/proxy-selection workflow. Report that boundary honestly.
No promise of automatically reconstructing intended geometry from arbitrary bad art.
A clean physical reference must also import/cook and agree with rendering/queries.

## 11. Existing runtime consumers must actually use the imported assets

Route normal model instances through existing public APIs and lifecycle mechanisms.

- Animation/Pose: one final resolved pose per appropriate animation instance; all
  skinned parts consume it, including high-index joints. No competing FBX player.
- Sockets/IK: use stable resolved joint identity and presentation/fixed timing;
  source reordering must not swap hands/feet or disconnect attachments.
- Ragdolls: mappings remain a physical subset, not a rigid body per imported bone.
  Enter from the resolved pose; every visual part follows through the normal skinning
  path. Keep accepted authored resistance and physics semantics intact.
- Renderer: all passes use the right per-skin palette/materials and conservative
  bounds. No disappearing boots/hair/shadows when only a limb leaves rest bounds.
- Scenes/prefabs: independent instances, part/material references, duplication,
  runtime spawn/destruction and undo remain coherent.
- Streaming: load/retire the complete dependency graph safely; do not turn parsing
  source FBX into main-thread region installation or retain stale import generations.
- Saves: cold restore of unchanged imported content preserves supported clip/mixer,
  skeleton-consumer and instance state using stable IDs. Incompatible source edits
  fail under existing content-compatibility rules rather than aliasing old handles.

Extend JudasJS only for genuinely needed generic model/clip/root-motion access,
using existing APIs when sufficient. Update declarations, reference, inventory,
manifest, cookbook and live coverage for every addition/change. No ImportMixamo,
SkateCharacter or native gameplay policy. Keep public compatibility or provide an
explicit documented migration; do not change existing primitive semantics casually.

## 12. Export and deliverable asset policy

## 14. Boundaries and final handoff

Required scope is import/runtime support/reimport/dependencies/diagnostics needed
above. It is not a DCC replacement or permission to combine future milestones.

Out of scope: arbitrary .blend/USD/CAD support; full source rig-constraint evaluation

base/static import may be useful, but is not a successful faithful animated import.
Do not use a long list of limitations to avoid required original-character support.

- Numerical/GL/consumer checks, final broad-gate/follow-up accounting, M56 timings,
  dependency/binary costs and known limits.
- Project paths, editor/CLI instructions, current docs, exact changes and final
