The project decides what content means, how it is discovered by gameplay, and
which published extension/replacement points it supports. This is not a native
inventory, weapon, quest, enemy, terrain simulation or game-mode framework.

## 2. Scope and explicit trust model

Required scope is local, developer-opted-in modding:
- Versioned .judasmod packages, manifests, dependency checks and deterministic
  resolution of a user-selected installed set.
- Additive content and explicit, game-authorized whole-resource replacements.
- Trusted local JudasJS mods, through existing scripting and callback machinery.
- Exportable game-specific modding kits and a usable editor/CLI authoring workflow.
- M75 terrain creation, sculpting, painting, cooking and terrain/map replacement
  through those tools, not just the ability to copy a cooked mesh into an archive.
- Local install, inspect, enable/disable, update/remove and useful diagnostics.
- Standalone runtime integration, save/load compatibility, Linux and Windows.

Modding is OFF by default. An ordinary unmodded project must retain its current
asset identities, scene behaviour, save semantics and export defaults. It must not
scan arbitrary Mods directories, execute discovered scripts or allocate an active
mod subsystem just because M76 exists. Opted-in games with an empty enabled set
remain usable.

IMPORTANT: CONTENT PERMISSIONS ARE NOT A JAVASCRIPT SECURITY SANDBOX.
The existing JudasJS runtime treats scripts as trusted project code. M76 must
preserve its current limits and not claim that a manifest confines a trusted mod's
runtime behaviour. Permitting a script gives it the ordinary exposed game-world
capabilities. It may affect entities, state or game policy through those APIs even
when it cannot replace the base script asset itself. Subscription ownership in
M73 does not make signal names a security boundary.

The game decides whether executable mod content is permitted at all. A user must
explicitly enable/trust that executable content before it runs; merely inspecting,
installing or listing a package must not execute it. A simple visible trust/enable
step and corresponding explicit CLI option are sufficient. Revalidate trust when
executable payload changes; an unchanged mod ID/version is not proof of unchanged
code. Do not run metadata extraction by evaluating an untrusted module first.

Data-only mode must inspect referenced scripts and scripted scenes/prefabs, not
just reject files ending in .js. A data-only package may instantiate specifically
published base behaviours through validated properties when game policy allows it;
that is different from supplying or replacing executable code. Trace indirect
references so an archive cannot conceal forbidden code in a dependency or alias.

Do not add Node, arbitrary OS commands, native DLL/SO loading, new file/network
bindings or package install hooks. Do not claim hostile-code containment from
QuickJS budgets, filename checks or the absence of those bindings. Enforcing
loader-owned content rules and safe filesystem operations IS required; isolating
malicious gameplay code is outside this trusted-mod milestone.

## 3. Game-authored mod contract

Add the minimum versioned project/export settings needed for a game's explicit
mod contract. Use existing appropriate identities and registries when possible;
do not identify a game by its display name, installation path or executable name.
Keep game compatibility, tool/content-format compatibility, save identity and mod
identity conceptually distinct even where existing fields can be reused.

The immutable exported game owns the authority to declare:
- Modding enabled/disabled, allowed addition types and executable-content policy.
- Published base asset references available to mod authors.
- Exact replacement targets or small named replacement groups, with required
  type/structural contracts and any expected compatible base revision.
- Named extension points and their bounded contribution descriptors, interpreted
  by the game's own code rather than native gameplay classes.
- Game/mod-contract versions and a bounded, documented compatibility rule.

Default-deny unpublished replacement targets. A mod cannot enlarge permissions,
rewrite the base contract, replace the startup project/executable/save identity,
or grant itself a capability by modifying its own manifest. Enforce the same
contract in editor validation, CLI packaging and the shipped runtime; bypassing
the editor must not bypass the loader's checks.

Whole-asset replacement is sufficient. Do not introduce arbitrary JSON patching,
script monkey-patching or semantic three-way merges. Types and required interfaces
must remain compatible: a texture is not a script; a prefab with expected script
properties must satisfy its declared schema. Reject a protected target even when
its bytes happen to be visible in the installed game's resources.

A declared dependency grants access to its published exports, not ownership of its
private files or permission to replace it. Supported registry use must be explicit:
mods cannot silently renumber base tags, input bindings, collision/render layers,
nav profiles or other numeric registries. Reusing the kit's published registries
is sufficient for v1; document/reject unsupported new registry definitions rather
than expanding every project-setting system.

If two enabled mods replace the same target, reject the ambiguous loadout with
both owners named. Dependency order or filesystem enumeration alone is not an
implicit override permission. A separately explicit game-authorized precedence
rule is optional only if it already fits the architecture; no general conflict
merge framework is required.

## 4. Package identity, dependencies and bounded IO

Use one versioned .judasmod distribution format. The outer container may reuse a
supported ordinary archive implementation; its extension does not justify new
model/texture/terrain serializers. Runtime payloads are existing cooked assets,
registered scripts, prefabs/scenes and other expressly supported ordinary content.

A manifest records stable mod ID, display metadata, package version, target game
and contract compatibility, required dependencies/versions, exported content,
contributions, requested replacements, executable-content declaration, and content
inventory with sizes/hashes. Include author/license/attribution metadata and retain
required notices. Identity and declared compatibility are not proof of authorship
or a digital signature; no signing PKI or license-policing system is required.

Choose a small documented version grammar. Exact versions or straightforward
bounded comparisons are enough; reject unknown syntax. Resolve only installed,
explicitly selected versions. No downloading, online resolver or SAT-based version
negotiation. Duplicate selected IDs, missing required dependencies, cycles,
incompatible formats/game contracts and invalid references fail preflight.

Build a stable dependency order with a documented stable-ID tie-break for unrelated
mods. Do not depend on directory order, timestamps, machine paths or hash-map
iteration. Save the actual selected/resolved order for inspection and compatibility.
An invalid requested loadout is not permission to silently drop a mod or launch a
partially modded save. Offer explicit correction or a separate no-mod launch.

Validate manifests and archive directories before allocation/publication. Set and
test finite caps for mods, dependency edges, metadata depth/counts, file count,
path length, per-file and total decoded bytes, extraction work and cache storage.
Check integer overflow and actual decoded output, not just declared sizes. Normal
M75 terrain products and their texture/navigation dependencies must fit a useful
v1 envelope. State the limits instead of designing only for the tiny lab.

Reject paths that can escape the package or collide after platform normalization:
absolute/drive/UNC paths, traversal through either separator, embedded NUL, Windows
alternate streams/reserved names/trailing-dot-space aliases, and duplicate or
case/Unicode-normalization-colliding entries. Define the portable path policy.
Preserve legitimate Unicode paths; do not turn all Unicode into a false error.
Reject archive symlinks/hardlinks and non-regular payloads unless an existing safe
policy already covers them. Never extract through an existing filesystem link into
base content or another directory. No shell interpolation for package paths.

Treat package corruption, truncated/oversized data, hash mismatches and unsupported
versions as actionable errors. Hashes establish integrity/content identity, not that
a downloaded script is trustworthy. Metadata inspection and rejected installation
must not create or execute content outside designated staging/storage.

Installation stages and validates the complete candidate before making it available.
Failed or cancelled operations retain the last good installed version and do not
modify the base game. Document actual crash/durability guarantees; do not describe
per-file rollback as filesystem-wide crash atomicity. Reuse existing publishers.

## 5. One effective content view, stable references

Compose a validated, immutable session content view from the base package plus the
selected mods. ResourceManager, script loading, scene/prefab construction, rendering,
physics, navigation and streaming must all resolve against that same view. Base
installation bytes remain unchanged. A private derived index/cache is acceptable;
physically overwriting Assets/ or weakening base integrity validation is not.

Freeze the effective package versions/bytes for the played session. Updating a
package on disk must not give an existing world half old and half new resources.
Use versioned retained storage or another demonstrated immutable snapshot policy.
Caches key content and relevant resolution identity, not a filename alone. Late
resource jobs cannot publish a different loadout's data into the current world.

Define namespace and reference rules before implementing remapping. Independent
mods can use the same relative filename or copied source-local identifier without
silently overwriting each other. Use qualified ownership and a stable validated
mapping to existing runtime AssetIds, or another compatible scheme. Check real
collisions explicitly; random regeneration on each load or dependency-order-based
IDs must not invalidate saves or cross-mod references.

Keep base AssetIds unchanged. Additive IDs never become replacements just because
they collide. Explicit replacements select a new effective provider for the allowed
logical target, preserving a consistent interpretation for all consumers. Referenced
replacement dependencies must resolve in their provider's context, not accidentally
bind a same-named base texture or another mod's script.

Apply established scene/prefab/region entity remapping and safe handle generations.
Entity identity is not asset identity. Maintain correct sockets, typed entity
properties, script slots, navigation/region references and restore references.
Do not globally search/replace decimal IDs in JSON or arbitrary JavaScript strings.

Provide a minimal supported way for gameplay and mod scripts to obtain published
contributions/references. Prefer validated descriptors and existing authored
properties where sufficient; add a small generic lookup/catalog API if necessary.
Names below are concepts, not an invented required signature: active mods, published
contributions, safe resolution of a declared exported asset or map. Return detached
bounded data, never filesystem paths/native handles or mutable loader internals.
Game JS chooses whether to list a map, instantiate a prefab or register an item.

Retain the ordinary virtual 'judas' module and module registration rules. Relative
imports must resolve from the owning registered module and stay within the allowed
package/dependency content. A package must not shadow the engine module, reach an
arbitrary host path with ../, or acquire private dependency modules by basename.
Do not promise to rewrite script-literal AssetIds. Use explicit exported references,
a qualified resolver or documented construction properties for relocatable content.

Executable contributions enter through ordinary authored script slots/approved
bootstrap entities and existing start/restore/fixed/UI lifecycles, not raw code run
during directory discovery. No new gameplay callback phase, VM per mod, hot module
reload or unowned global initialization convention. M73 signals can communicate
between trusted scripts; no automatic broadcast of every engine event is introduced.

Preflight before activating scripts or replacing a live world. Document which
structural/reference/cook checks are eager and which existing resource decodes are
asynchronous. A later script exception follows existing slot-fault rules; do not
claim arbitrary gameplay side effects can be rolled back by uninstalling a mod.
Errors must retain mod/asset/phase attribution so the user can identify the owner.

## 6. Usable install and selection workflow

Provide inspect, install, list, enable/disable, update/remove and validate operations
through a small editor/tool workflow and matching CLI. Users must be able to use
installed mods with the standalone game, not only by opening its source in Judas.
A compact prelaunch selector/launcher or another discoverable non-code workflow is
enough; no polished online browser is required.

Use a game-specific writable user-data location through current platform services.
Read-only installation directories must work. Optional adjacent Mods/ discovery can
be supported, but must not be the only path or grant arbitrary write locations.
Do not install mods in Saves/ or require administrator rights. Installed payloads,
selected loadout, temporary staging/cache and save slots have distinct ownership.

Changes take effect at the next fresh played session or process launch. Requiring a
restart is acceptable and must be visible. Do not hot-mount/unmount active resources
or scripts. Uninstalling an in-use version must be deferred/refused, not invalidate
live file reads. Dependents receive useful diagnostics. Removal deletes only the
selected mod's owned installed/cache data; it never removes base/shared assets,
another mod, authoring work or save slots.

A failed update keeps the working version. Do not overwrite locally edited mod
source: editable authoring projects are distinct from installed immutable packages.
Expose diagnostics for enabled versus installed, compatibility, dependency order,
replacements and the resolved active signature. Add an explicit no-mod launch path
that leaves files and existing loadout settings intact.

## 8. Terrain tools are a REQUIRED mod-author workflow

Reuse the actual M75 TerrainAuthoring/TerrainDraft/CreateTerrain/ForkTerrain/
CookTerrain services and viewport tools. Do not rebuild brushes in a mod editor,
require an external terrain application or claim that packaging a prebuilt mesh
satisfies this requirement.

A mod author must be able to:
1. Open a kit-bound mod project without the original game source.
2. Create a new .judasterrain, or fork a terrain source deliberately provided by
   the kit, with new writable source/product identities.
3. Raise/lower, flatten, smooth and paint through the real editor; Undo/Redo,
   save/reopen, cook and place it in an ordinary map/prefab.
4. Bake relevant navigation against the intended effective collision geometry.
5. Validate/export a .judasmod, install it and use it in the untouched shipped game.

Keep editable terrain and other source artifacts in the authoring project or an
explicit developer kit/source deliverable. Runtime mods need ordinary cooked model,
texture, collision and navigation assets, not brush services or raw terrain source.
Packaging checks freshness/provenance before export; runtime requires verified
cooked payloads, not the developer's receipt paths or unavailable source project.
Do not bypass M75 freshness checks just because authoring occurs in a mod project.

Terrain replacement is a CONSISTENCY problem, not merely a texture substitution.
The same composed session must use matching render geometry, collision, declared
material dependencies and any geometry-dependent navigation bake. Permit replacement
of an explicit bundle or terrain-bearing prefab/scene where that is the clean
existing boundary. A mod replaces all required products together, or is rejected;
never display a new hill over old collision or accept stale navigation underneath.
The kit must supply the geometry/authoring references needed for permitted rebakes.
Missing private source is not justification to claim a stale bake is valid.

Weights/tiling-only paint retains M75's geometry behaviour. Changing palette resource
identities currently has broader freshness effects; preserve/document that existing
contract rather than claiming all appearance changes are geometry-independent.
Prove both new-map addition and an allowed replacement of a base landscape. A
protected landscape remains unreplaceable. Two replacement mods conflict clearly.

Retain M75's finite static open height-patch limits, four base-colour layers, unit
collision scale, arbitrary rigid orientation and independently authored gravity.
No caves, automatic seams/LOD, spherical sculpting, terrain runtime brushes, dynamic
navigation baking or water coupling is added here. Do not change accepted radial
terrain/fluid behaviour. The mod tools expose supported capabilities honestly.

## 9. Other ordinary content and packaging completeness

baked animation and other supported registered types should follow the existing
pipeline where valid; publish an explicit support matrix. Do not claim every engine

invent complete dependency discovery by scanning JavaScript strings. Modules, UI,

content-only mod should be portable between matching Linux and Windows game builds;
normal platform runtime libraries belong to the game, not the mod archive.
