## 2. One document model and one editing path

Editor widgets, viewport tools, source editing and shipped CLI operations must
converge on the same validated documents, references and command semantics.

Use the existing command/undo and serializer infrastructure. Extend the smallest
shared document/property description needed; do not create a second scene database,
entity-ID scheme, generic scripting language or parallel JSON-to-runtime engine.

Every meaningful authoring operation must have a defined result:
- Validate before publishing. An invalid batch must not leave half of its edits live.
- One user action is one coherent undo transaction, including dependent reference
  remaps and authored prefab overrides. Redo must reproduce the same identities.
- Continuous dragging creates one undo action on release, not hundreds of entries.
- Cancellation restores the pre-action document. Selection changes are not edits.
- Dirty state, validation errors, generated products and unsaved source are distinct.
- Play uses a runtime instance; Stop must not leak simulation changes into authored
  content. No new implicit 'save runtime back into the scene' behaviour.

Cross-file operations need staging and recoverable publication. Do not promise
filesystem-wide atomicity from several independent renames. Validate all affected
outputs, keep a recovery path, and prevent a partially published set becoming the
editor's active project. Never overwrite an external edit unnoticed.

## 3. Productive hierarchy, selection and everyday level editing

Turn M65's initial facilities into a coherent workflow, not duplicate checkboxes.

Hierarchy and selection:
- Search/filter by name, component/type, tag and useful asset/reference identity;
  show matching descendants with enough ancestor context to find them.
- Reliable range/add/toggle selection and viewport selection; selecting a hierarchy
  parent and child must not apply a world transform twice.
- Distinguish organizational folders/groups from transform parenting. Organizing a
  level must not unexpectedly move bodies or change gravity/reference relationships.
- Reparent with an explicit preserve-world/local policy, cycle checks and clear
  diagnostics when the current transform/scale contract cannot represent the result.
- Keep stable selection across sorting/filtering; identify inactive streamed content
  by qualified authored identity, not by a recycled live handle.

Transforms and properties:
- Shared-pivot versus individual-origin transforms, local/world axes, numerical
  entry, translation/rotation/scale snapping, alignment and distribution.
- Clear mixed values and explicit set-versus-offset semantics. Apply only edited
  fields; do not fill untouched mixed values from the first selected object.
- Add/remove/copy/paste common components with compatibility preview and undo.
  Explain why a field/action is unavailable instead of silently skipping objects.
- Supported surface placement/snapping should use normal collision/query geometry
  and an explicit orientation policy. Do not equate the hit normal with gravity.
- Batch rename, duplicate, delete and reference inspection must preserve/remap the
  right identities and show affected dependencies before destructive changes.

Preserve physics scale restrictions. Provide explicit bake/convert paths where
already supported; do not silently normalize a transform or scale a collider in a
way the runtime does not actually support.

## 4. Build geometry and repeated content without an external generator

Provide a deliberately small, reusable set of authoring tools:
- Linear and radial arrays of entities/prefabs.
- Editable paths supporting straight segments and smooth curves, with spacing-based
  placement, orientation/twist control and stable local frames.
- Generic profile extrusion/sweep and arc-based construction sufficient to make a
  bank, curved ramp, quarter-pipe, ledge or corridor section.
- Preview, parameter editing, validation, apply/cancel and coherent undo.

These are offline/editor content tools, not native skateboard or parkour systems.
Recipes produce ordinary meshes, collision sources and entity/prefab instances.
Do not start a full CAD modeller, terrain editor, arbitrary CSG engine or runtime
procedural-world framework.

Keep the editable recipe. Re-editing a radius/width/path/spacing should not require
starting again or manually rebuilding thirty objects. Stable recipe-element IDs
must preserve surviving instances, overrides and references through regeneration;
changing array order is not permission to rename every entity. Explain removal of
referenced elements and allow an explicit bake/detach operation when appropriate.

Generated topology must pass M64's actual cooking checks. Closed-source options
must have coherent winding/caps and no generator-created T-junctions or internal
barriers. Decorative render detail need not become collision detail. Allow a clean
lower-resolution physical proxy from the same recipe, with visible accuracy limits.
Do not relax the cooker to make bad output pass.

The shipped editor and CLI use the same recipe evaluator. Routine previews should
cache unchanged work and schedule expensive generation/cooking through existing
jobs. Stale preview results must not overwrite newer parameters or a different
project. An accepted preview must match the committed/cooked result.

## 5. Imported assets, physical authoring and practical skeleton tools

Put M66 into the normal world-building loop:
- Browse/search assets by useful type/status, inspect dependencies and users, locate
  source/import recipe, place multipart models, and create/reuse prefabs.
- Show imported defaults, authored remaps and instance overrides distinctly; provide
  reset/apply/revert operations with clear scope and undo.
- Reimport must retain M66 stable subassets and last-good recovery. Do not re-solve
  import mathematics, reduce the rig or introduce an external DCC prerequisite.
- Expose collision source/selection, supported proxies, cook/rebuild and stale status
  beside the model. Link located face/vertex errors to the actual preview geometry.

Skeleton/physics authoring must work with a real multipart imported character:
- Search/select joints, show hierarchy and local axes, and inspect sockets/IK targets.
- Author and batch-edit ragdoll mappings, bodies, joint frames and limits without
  typing every full joint path or calculating Euler frames in a private Python tool.
- Provide a previewable, explicitly accepted fit-to-selected-bones/chain helper for
  supported body shapes and anchors. Limits, resistance and mappings remain editable;
  geometry-based guesses are not an automatic proof of anatomical correctness.
- Preserve unmapped bones and existing valid mappings, including accepted physical
  resistance. Non-humanoid names must work; no hidden Mixamo-specific engine branch.

Make existing navigation, liquid, cloth/deformable and fracture asset references,
source/cook controls and validation reachable through ordinary inspectors. Where
an existing cooker has only a CLI entry point, expose that shared service rather
than a second cook implementation. Do not add fracture/remeshing algorithms or
promise automatic repair of arbitrary malformed art. Authoring offline-cooked data
is legitimate; needing an undocumented private script to do it is the problem.

## 6. A first-class named authoring format, not another disposable converter

The M68 half is REQUIRED, not an optional documentation appendix.

Provide a documented, versioned, named-field authoring representation for at least:
- Project settings, registries, input maps and export scene selection.
- Scenes: hierarchy, components, typed references and existing component settings.
- Prefabs and their supported overrides/reference remapping.
- Runtime UI documents: elements, layout, style, localization and event-facing IDs.
- Existing world manifests and the authoring recipes introduced here, through the
  same validated reference/document conventions.

Prefer extending the existing JSON authoring path. Do not add YAML or invent a DSL
merely for appearance. Each file declares its document kind and authoring schema
version. This version is separate from canonical scene fingerprint schema 5,
save-format versions and runtime/cooked-asset versions.

A developer must be able to create/open a named document in the editor, edit it in
text, return to the editor, and save/export it without losing settings or references.
A write-only 'JSON generates positional text; editor later edits a different truth'
pipeline does NOT satisfy this milestone.

Choose and document one authoritative editable representation per document.
Cooked/positional runtime products may remain for compatibility or loading speed,
but must be clearly derived when used that way. Do not allow two independently
editable files to silently overwrite each other. Preserve legacy readers and
lossless handling of existing assets; migrate only explicitly selected working
copies, never historical evidence or all existing projects behind the operator's back.

Named forms need complete round-trip coverage of current fields in the supported
document families, not just the three settings used by the new demo. Build a coverage
matrix from actual serializers/components. A still-unsupported field must block a
lossless conversion with a precise message; never drop it and call conversion successful.

## 7. Format semantics, identity and compatibility

Document types, defaults, required fields, units, reference forms and ordering.
Use invariant numeric parsing/writing regardless of process/user locale; support
normal Unicode names/text. Reject non-finite transforms and malformed bounded data.

References keep existing stable project/asset/entity/subasset identities. Friendly
paths/names are for discovery; renaming a display label must not retarget a reference.
Cross-region references retain existing qualified identity, remap and pin semantics.
Do not reconstruct a JS VM per inspector or dependency check.

Make diffs useful:
- Deterministic formatting/property order; omit no meaningful state accidentally.
- Preserve semantically ordered arrays such as script slots and pose layers.
- Whitespace/property-order changes must not change normalized authored meaning.
- Unknown versions/types and duplicate keys receive explicit diagnostics. Optional
  extension data needs a documented preserve-or-reject policy; no silent loss.
- Preserve existing canonical fingerprints for unchanged legacy state. Source-file
  provenance hashes may change with text; do not confuse those with semantic identity.
- Continue M61 compatibility checks. A new text format does not authorize loading
  incompatible game saves or rewriting their fingerprints to make them pass.

Provide explicit migrations for versions introduced by this work and examples of
reading existing content, writing named content and converting back where supported.
Use semantic/round-trip comparison to show identity and behaviour are preserved.
A formatting-only round trip must not regenerate all asset IDs or dirty the project
perpetually. References into unsupported transform/topology changes must be reported,
not guessed.

## 8. Supported CLI and source editing

Extend the existing authoring executable rather than inventing a separate toolchain.
Provide documented operations equivalent to:
- Create/inspect supported documents and templates.
- Validate with diagnostics and nonzero status for invalid input.
- Convert legacy/named forms, with dry-run and explicit overwrite policy.
- Apply bounded batch/property/reference edits through the normal validators.
- Generate recipes and invoke existing import/cook services.
- Show a semantic diff and dependency/affected-reference summary where useful.
- Validate/build a project for normal export.

Exact commands are your choice; document actual commands, not hypothetical examples.
No network service, Blender or handwritten positional-file emitter should be required
for the supported ordinary workflows. Small automation scripts may orchestrate these
shipped tools; they must not secretly replace missing engine authoring functionality.

Offer a source view/edit workflow for the named documents. Syntax/semantic errors
should identify file, line/column where available and a field path/entity/element.
Distinguish unknown property, wrong type, unresolved reference, duplicate ID, invalid
geometry and stale cooked data. Show actionable context instead of 'invalid settings'.

External edits: detect divergence from the loaded version, present a diff/reload or
conflict choice, retain dirty work, and publish valid changes coherently. Invalid
external edits must not destroy the last-good document/runtime asset. Do not promise
arbitrary live gameplay hot reload; restart/reload policies may remain explicit.

## 9. Runtime UI authoring must be genuinely usable

Bring the M41/M58 UI workflow into the shared document/command system:
- Visual hierarchy/canvas preview, element selection, anchors/offsets/sizing,
  containers/padding, alignment, clipping and localization-aware text preview.
- Useful element duplication, copy/paste, batch styling, preview sizes and undo.
- Inspect effective layout and inherited/container-driven values so a developer can
  understand why an element ended up there. Identify controls owned by a layout parent.
- Editor measurement/preview and runtime must use the same shaping/layout semantics;
  preserve RTL, fallback, wrapping, baselines and exposure-independent text.
- Direct text editing and visual editing must agree on the same element IDs and
  properties. No separate editor-only layout that changes on export.

Close Void S6 with safe runtime layout access for existing UI elements: scripts must
be able to move/size supported elements or update appropriate anchors/offsets through
a documented API, without rebuilding the entire document. Runtime-only changes are
transient unless explicitly captured through existing game-state policy.

Layout changes must invalidate the correct caches and keep drawing, clipping,
hit-testing and focus geometry consistent. Batch updates should not trigger a full
layout rebuild for every property write. Do not add rich text, a browser engine,
IME, a new widget framework or a gameplay HUD system.

## 10. Close the small authoring-to-runtime seams exposed by Void

These three practical capabilities belong in this combined milestone. First check
whether M66/current source already supplies any part; do not add duplicate APIs.

A. Camera projection and overlay placement (Void S2, complementing S6)
- Author and control near/far clipping for script-owned views and applicable camera
  components. Preserve existing defaults. Validate finite values and near < far.
- The same projection must drive rendering, culling, view rays and any viewport
  projection query; do not fix only the matrix in one render pass.
- Supply/reuse a generic world-to-viewport projection helper so normal scripts can
  position UI markers; return meaningful behind/outside/depth information.
- Demonstrate an object beyond the old 500 m cap with a suitable configured view,
  and an indicator following it in first/third-person cameras and on window resize.
- Explain depth-precision tradeoffs; no claim of infinite viewing distance, live
  origin rebasing, new shadow algorithms or an orbital/space-camera framework.

B. Runtime UI placement is the safe layout interface specified above, not a native
TargetMarker feature. The game decides what to label, hide or clamp to the screen.

C. Prefab construction data (Void S8)
- Allow bounded, validated per-instance initial properties/state and relevant
  existing transform/body initialization through the normal spawn path.
- Validate and apply these before start/first simulation observes the new instance.
  Specify ordering with resource readiness and script lifecycle explicitly.
- Resolve permitted entity references safely; keep independent instances isolated.
  Failed initialization must not publish a partly configured live hierarchy.
- Respect M61 restore: loading is not a second fresh spawn that reapplies defaults
  or calls start twice. Preserve ordinary existing spawn behaviour without options.
- Demonstrate independent debris-like instances with different initial motion/data
  without a module-global pending-initialization map. No DebrisManager native feature.

Any public addition gets the normal JudasJS declarations, reference, inventory,
machine/live coverage and executed cookbook update. Document coordinate spaces,
validation, lifetime, snapshot/mutation and phase semantics; do not expose raw pointers.

## 11. Editor coherence and visual usability

This is part of acceptance, not permission to spend weeks replacing ImGui.

Use a compact, consistent desktop-tool layout: clear hierarchy and selection,
readable typography, consistent units/labels, meaningful spacing and predictable

## 13. Responsiveness, jobs and lifecycle

Use M56 to measure editor work, not just game FPS. Record selection/filter latency,
batch edit/undo, path/array regeneration, cooking, layout preview and source reload
on a stated document size. Include warmed median/p95/max and one cold run.

Typing or selecting should not repeatedly parse/copy the complete project, rebuild

Renderer work stays on its proper boundary; worker parsing/cooking must not call

Write focused regressions as each coherent feature lands. Required coverage:

UI / PUBLIC APIS

## 15. Boundaries and final handoff

- A new physics engine, collision algorithm rewrite, new liquid/cloth/fracture solver.

- A replacement UI runtime, shader graph, cloud collaboration, plugin marketplace,
  language server, browser editor or arbitrary gameplay hot reload.
- Comprehensive import/streaming performance research or speculative runtime features.
- Native game semantics, a redesign of the three games, or unrelated issue cleanup.

Preserve protected research/history, existing accepted projects and physics/fluid
behaviour. Update CURRENT docs to explain new authoring paths and supersession;
