# Developer workflow pass — operator review

1. Open docs/judasjs/examples/developer_workflows/developer_workflows.judasproj.
   Play: read visible controls, move, push the orange crate and drive/brake the car.
2. Open View → Diagnostics and extensions → Runtime Inspector. Compare root and
   streamed yard owners, body/proxy presence, script phases and stable references.
3. Pause, R to request yard: it can prepare but installation waits for resume.
   Resume, push the blue crate, release/re-request and verify its counter returns.
4. Request a region through World regions twice. One editor lease should remain;
   Release should not cancel a separate gameplay request. Inspect retention reasons.
5. F6, quit fully, reopen and F9. Check actual vehicle/driver and both crate states.
6. Work on a disposable project copy. Disable the yard script: collision can exist
   without its gameplay registration. Read the explicit not-registered/fault status.
7. Change runtime content in another copy; an old save should explain the mismatch
   before replacing the world. Preserve original saves and matching game builds.
8. Open guide links from the editor. Follow the short lessons without internal
   engine knowledge. Try dark/light, your UI scale and a saved workspace layout.
9. Move the entire standalone package and launch from elsewhere. Judge the visible
   HUD and interactions yourself. The teaching geometry is deliberately simple.
10. Reopen Lunar Island and check flight/normal gameplay still feels right.

Automated results do not confer human acceptance, clean-machine support, Windows/
Android/controller qualification or universal readiness/persistence compatibility.
