# Real Linux SDK packaged-entry regression

The Windows-discovered issue also reproduces on the existing Linux SDK. Earlier
Linux qualification invoked `tools/inspect_sdk.py` from the source checkout while
inspecting the staged SDK; that proved native loader/ABI behaviour but did not
exercise the inspector **installed inside the checksummed SDK**.

## Actual failure and correction proof

Nine commands completed with their expected exits. Plain Python was used, with
neither `-B` nor `PYTHONDONTWRITEBYTECODE`; `PYTHONPYCACHEPREFIX` was also absent.

1. Create an owned copy of the original SDK using hardlinks for existing files and
   separate directories. No existing hardlinked file is ever modified. Strict
   verification initially passes.
2. Execute that copy's **packaged** inspector. Its imports create
   `tools/__pycache__/binary_dependencies.cpython-314.pyc` and
   `package_sdk.cpython-314.pyc`. The inspector then rejects its own mutated payload
   with `SDK file inventory/checksum mismatch`, exit **1**.
3. Strict verification afterward also fails, exit **1**. The original SDK remains
   byte-for-byte untouched. Exact generated-file hashes and original failure
   output are preserved; generated bytecode is not added to tracked evidence.
4. Stage a **new** ordinary SDK using corrected source tools, the existing build's
   17 real Release executables, its original build information and `--probe-tools`.
   No CMake configuration, C++ rebuild or binary identity rewrite is performed.
5. Strict verification, the new **packaged** inspector's actual ELF/architecture
   and native loader checks, packaged Android verifier `--help`, and strict
   post-verification all pass. The corrected SDK's complete file inventory and
   bytes remain identical, with **no `__pycache__` directories**.
6. Add an unexpected `.pyc` only to a separate negative-control copy. Strict
   verification still rejects it, exit **1**. No whitelist or ignored-cache rule
   was added to the manifest verifier.

The two corrected Python source hashes are:

| Tool | SHA-256 |
|---|---|
| `inspect_sdk.py` | `e4017421e901809aaee1b46f12f89dc248151f0100136effad0646c996b3da4b` |
| `verify_android.py` | `2d147363d310cdaa5394af29377f0a4981585b2c2f0caf05cbf5357430c4a9d2` |

Each sets `sys.dont_write_bytecode = True` before importing SDK-local helpers.
`package_sdk.py` and its strict inventory/checksum policy remain unchanged.

## Identity and scope

The source base is `9deb47d1667e5b6bd1abe708ed343c3fbf6fe847` plus the two Python
edits. Native binaries retain their **actual** already-tested
`60a9217-dirty-f08fa44808d9` provenance (the byte-equivalent scripting-literal
candidate); they are not relabelled as newly compiled. All **17** binary bytes are
unchanged. Source tool hashes, original/corrected manifests and exact native binary
hashes are separately recorded. The corrected SDK manifest SHA-256 is
`cc45ef61edac13bc476f8d2256d9732f0a95413bf55dcb5a13343fa68434c2a5`.

This is genuine Linux packaged-tool qualification. The Android `--help` case proves
read-only import/entry behaviour, **not** APK verification, device functionality or
hardware acceptance. The native inspector proves this host's 17 executables load;
it does not expand their previously recorded ABI/platform compatibility.

with the preserved original SDK and existing build binaries, then execute with
ordinary Python. Use fresh owned output paths. No engine implementation, compiled
binary, protected history, research or original SDK payload is changed by this
verification.
