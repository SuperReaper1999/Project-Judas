ROOT CAUSE AND CORRECTION

There are three different quantities:

  1. Ordinary support impulses estimated by the current fixed-step solve.
  2. Additional impulses needed for a later, genuine impact in that step.
  3. Completed actual contact reactions published to observers/controllers.

The earlier growing-impact correction separated (2) from re-projecting an
entire stack's unrelated resting residual. But WorldImpactEvents.cpp still
erased (1) whenever that event changed an endpoint velocity. Repeated events
therefore cold-started the next ordinary ten-sweep solve. The less accurate
finite-pass support solution produced additional motion and impacts, which
erased more guesses. The trace measured thousands of erased support entries
per step. This was feedback across fixed-step boundaries, not merely a slow
triangle primitive or insufficient GPU rendering speed.

The correction preserves the ordinary support guesses inside the EXISTING
continuationEligible branch. It does not apply them during the event, copy
event impulses into them, or treat a cached contact as fresh geometry.

At the next ordinary step, native geometry, body generations, primitive IDs,
normal agreement and nearest unused anchors still determine whether a guess
matches. ContactSolver prepares fresh frames/effective masses, reprojects the
friction guess and applies it once as an iterative initial estimate. The
normal/friction iterations can subtract excess accumulated impulse. Changed
velocities alone do not make that initial estimate invalid.

New event-only groups retain zero-load identity. Actual completed event loads
continue to replace their own observation groups separately. Hard joints,
external velocity coupling, elastic flights and unsupported geometry retain
their previous invalidation/fallback policies. Existing sleep quietness gates
and generation/ownership checks remain; no forced sleep is introduced.

Only src/physics/WorldImpactEvents.cpp changes runtime behavior. It becomes
smaller. PhysicsWorld remains the existing coordinator; there is no new graph,
public API, component, save format or alternative physics world.

CAUSAL PROOF, NOT JUST A FASTER PILE

The new active SupportGuessOwnershipTests.cpp exercises an actual warmed box,
floor and separated projectile impact. Both implementations produce the same
15.47565 m/s immediate target response. The old code discards all four ordinary
support guesses; the corrected code preserves all four, bit for bit from the
ordinary solver producer. Actual projectile impact reaction is independently
observable, while its new warm identity has zero impulse.

The exact same corrected fixture fails only the intended preservation assertion
against the original core (55 checks, one failure), and passes against the final
core (59 checks, zero failures). Counts differ because positive producer rows
exist only in the corrected cache. This is not a new timing threshold.

Private paired physical checks additionally cover mass/inertia changes,
separation, tiny and large actual impacts, elastic return, rotated gravity,
finite support departure, disabling/moving/masking/suppressing supports,
sensor changes, slot reuse and reset. The lifecycle pair retains all 98 recorded
physical outcomes exactly, including real gravity flight; only the intended
immediate warm estimate differs. Invalid history is discarded by subsequent
native matching. Completed observation revisions are not falsely described as
the ordinary cache's invalidation mechanism.

NUMERICAL CHANGE

Dense pile trajectories DO change: the same finite-pass solver now starts from
better retained estimates. This is not bit-identical physics versus the old
pile. No force, impulse, velocity, contact-depth or iteration threshold was
retuned. The existing inelastic energy guard and prescribed-boundary work
accounting remain. The 1,800-step final run matches every physical/work row of
the private corrected control exactly, and an independent final 900-step run
matches its prefix. These are corrected-repeat comparisons, not old/new parity.

WHY THE BUSY PHASE STILL HITCHES

In the final live capture, fixed steps during wall seconds 10–20 average
17.26 ms, already over the 16.67 ms physics interval before rendering/runtime
overhead. The unchanged accumulator consequently runs multiple steps per
displayed frame. Their average is about 5.6 steps/frame in that window; a
212.8 ms frame is not a single 212.8 ms collision solve.

Actual recorded mean coarse times there: rigid physics 16.32 ms, contact
generation 4.82 ms, combined solver/impact phase 5.53 ms, broadphase plus
end-of-step bookkeeping 3.12 ms. These are existing inclusive/coarse timer
boundaries, not disjoint CPU sampling percentages. The remaining work needs
roughly a few milliseconds/step reduction to sustain both 60 Hz simulation and
30 FPS rendering throughout. It is not established to be unavoidable hardware
cost, nor is every remaining collision request proved redundant.

A bounded exact row-dependency prototype was tested on top of the correction.
Its positive/negative controls pass and all 900 physical/work rows match, but
native mean time is 17.78→17.93 ms: no demonstrated net benefit. Its complexity
is NOT adopted. An initial llvmpipe run is retained as an invalid timing
comparison; the subsequent native NVIDIA run provides the quoted result.

The separate SAT-feature/face-continuation prototype remains source-only,
unqualified and unused. A larger persistent graph is not introduced merely to
satisfy the initial architectural proposal when the measured primary defect
is a wrong history-ownership rule. Earlier unsuccessful warm-retention research
is also preserved: it predated the growing-impact correction and did not solve
re-projection of the entire resting island. That earlier failure is not
retroactively relabelled a success.
