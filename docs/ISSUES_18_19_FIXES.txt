#19 — confirmed renderer defect, corrected
The previous weather compositor substituted fixed daylight colours for the scene
background. Cloud, fog, funnel and precipitation illumination also contained
fixed daylight terms. Rendering the flight game's night settings produced the
same sky as daytime; a zero-light below-horizon control did too.

The renderer now forwards scene ambient/background alongside its existing sun
colour/direction to weather programs. A continuous artistic lighting response
blends dim authored sky with the procedural daylight gradient. Background/sun
chromaticity tints that gradient; weak moon lighting does not activate daylight.
Legacy background colours are decoded before compositing; linear/HDR follows its
existing path. Clouds/fog/precipitation/funnels use actual scene illumination;
lightning remains independently emissive. Weather-off output, quality bounds,
origin anchoring, depth clipping and authoritative CPU wind/forces are preserved.
This is prescribed artistic weather, not a physical atmosphere/day-night clock.
Custom environment-image sky compositing remains outside the weather sky path.

Initial background-only approach broke the original sunny-weather check for
scenes using default backgrounds. Its failure is retained. The final light-driven
blend passes that original threshold/fixture unchanged. An early new cloud test
used a screen-brightness ratio despite nonlinear encoding; it was replaced with
strong independent zero-light/emission and ambient-only controls. The original
failure and subsequent dusk-colour regression outputs are preserved honestly.

#18 — two distinct confirmed problems
1. Harness pointer position previously changed only legacy UI coordinates.
   Gameplay input.pointer could remain(0,0,false) while ui_click was held.
   Window's test adapter now synchronizes position/primary held state with the
   ordinary logical bindings. It is gated to explicit test mode. Queued inputs
   use the same adapter; UI/editor ownership clears injected held state.
   The application harness adds POINTER_DOWN/UP, TOUCH_DOWN/MOVE/UP,
   EXPECT_POINTER and EXPECT_TOUCHES. Contact lifetime and malformed input fail
   with diagnostics. Existing POINTER/CONTROL/ACTION commands remain supported.
2. BlockSmasherV2's game-side pointerInput sampled only pointer.down in fixed
   callbacks. A completed click between callbacks was absent from that snapshot.
   The engine DID retain pressed/released edges; no general logical-edge defect
   was established. A project-owned pointer_press action bound to mouse:Left
   supplies those edges to the game's existing tap/drag detector. Two JS lines
   plus one binding fix short mouse taps without firing on press during a drag.
   No game-specific engine system, pointer-down latch or new JudasJS API added.
