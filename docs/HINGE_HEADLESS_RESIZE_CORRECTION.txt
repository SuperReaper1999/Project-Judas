ESTABLISHED CAUSE
SDL_GetWindowSize, SDL_GL_GetDrawableSize and a direct XGetWindowAttributes
query ALL report the correct new360x800 size. The X window has already resized;
absence of a window manager does not explain an incorrectly sized native window.
The actual GL backing storage retains the old dimensions until a presentation
boundary. A small independent SDL/GL pixel probe allocates the original buffer,
resizes, clears and reads a far pixel. Pumping events, making the same context
current, unbinding/rebinding it, show/hide and glXWaitX do not refresh the buffer.
SDL_GL_SwapWindow does: the far pixel changes from black to the cleared green.

The ordinary runtime swaps frames; a non-realtime capture-only harness can omit
all swaps. The previous resize implementation updated window/input state without
completing the presentation boundary needed by this driver. NVIDIA real-X11
passed the original tests; that did not establish Mesa/Xvfb support. Earlier
restricted-environment failures used SDL offscreen, which is a separate retained
unsupported backend. The earlier claim that Xvfb could simply be substituted
was insufficiently verified. Original reports and failures remain untouched.

CORRECTION
Window::Resize now completes one SDL_GL_SwapWindow after native event pumping
and before successful return. The next draw/readback therefore uses refreshed
backing storage. No sleep, polling-until-pass loop, window/context recreation,
fake framebuffer, image padding/cropping or gameplay/render-quality change.
Queued hardware events are still not routed into deterministic harness input.
The existing explicit offscreen and Android resize rejections are unchanged.
This is a bounded operation per requested resize, not per physics step/frame.
Ordinary runtime presentation cadence and the fixed simulation clock are unchanged.
